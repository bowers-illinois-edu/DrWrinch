# DrWrinch Shiny app: implementation plan

This document captures the implementation plan produced by a planning
agent on 2026-05-19. The plan is referenced from `HANDOFF.md`. Read
both before starting.

## 0. Grounding from the codebase

What's actually there:

- Four exported functions in `R/bf_binomial.R`, `R/bf_urn.R`,
  `R/sens_binomial.R`, `R/sens_urn.R`; one internal
  `.find_omega_tipping()` in `R/utils.R`.
- `DESCRIPTION` declares `Depends: R (>= 4.0.0)`, `Imports: stats,
  BiasedUrn`, `Suggests: ggplot2, dplyr, knitr, rmarkdown, testthat (>=
  3.0.0), DrBristol`. Version is `0.0.0.9002`, CRAN submission pending
  (`cran-comments.md` exists).
- `inst/` currently holds only `CITATION`. No `inst/shiny/` yet.
- `tests/testthat/` has three substantive test files; `testthat`
  edition 3.
- `.Rbuildignore` is minimal; nothing about
  `shinyapps.io`/`rsconnect` yet.
- The vignette (`vignettes/getting-started.Rmd`) is the canonical
  narrative the UI should mirror: paper example is `y_W = 7, y_R = 3`;
  threshold default is 20; `sens_urn(7, 3)$omega_star ~= 1.304`;
  `bf_urn(7, 3) = 39`; `bf_binomial(5, 5) = bf_urn(5, 5) = 1`.
- Coding standards (`~/repos/ai_workflow/CLAUDE_CODING.md`) require:
  tests-before-implementation, "why" comments at branch points,
  `devtools::document()` + `devtools::check()` before complete,
  one-file-per-coherent-unit (files ~< 300 lines), bump patch on new
  exports, **pause for review** after tests, after implementation, and
  at any unresolved design decision.

Constraints this places on the plan:

1. The app is essentially a thin GUI over four pure functions. Do not
   over-engineer.
2. CRAN cares about: examples that do not block (`\dontrun{}` for
   `run_app()`), `inst/` size (Shiny apps with heavy CSS/JS bloat the
   tarball), and that every package in `Suggests` is used only after a
   `requireNamespace()` guard inside `run_app()`.
3. The four functions already do all the validation we need --- the
   server's job is to translate Shiny inputs into well-formed calls,
   catch the documented `NA_real_` / `Inf` outcomes, and render them
   with prose a non-R user understands.

## 1. File-by-file scaffold

### 1a. New code in `R/`

**`R/run_app.R`** (new, ~40 lines)
- Exports `run_app()`.
- Signature: `run_app(launch_browser = interactive(), ...)`. The `...`
  is forwarded to `shiny::runApp()` so power users can pass `port`,
  `host`, `display.mode`, etc.
- Body, in order:
  1. `requireNamespace("shiny", quietly = TRUE)` --- if missing,
     `stop("Install 'shiny' to use run_app(): install.packages('shiny')", call. = FALSE)`.
     Repeat for `bslib` and the chosen plot library. **Why** at
     runtime, not as hard Imports: keeps CRAN tarball small and keeps
     `R CMD check` honest about what's actually needed to use the core
     BF functions from the command line.
  2. `app_dir <- system.file("shiny", package = "DrWrinch")`; if
     `app_dir == ""` stop with a helpful message ("did you install
     from source without inst/?").
  3. `shiny::runApp(appDir = app_dir, launch.browser = launch_browser, ...)`.
- Roxygen with `@examples \dontrun{ run_app() }` (blocks otherwise) and
  `@export`.
- Cross-references: `@seealso [bf_binomial()], [bf_urn()]`.

Do **not** add any module/server R files under `R/`. Keep everything
under `inst/shiny/` so the app dir is self-contained and can be
deployed independently to shinyapps.io without dragging the rest of
the package source.

### 1b. App under `inst/shiny/`

Use `ui.R` + `server.R` + `global.R` (rather than a single `app.R`)
for three reasons: (i) shinyapps.io and `rsconnect::deployApp()`
recognize either, (ii) `global.R` is the conventional place to put
library calls and helper sourcing that needs to happen exactly once at
app start, (iii) it makes the file-per-coherent-unit rule easier to
honor without 600-line `app.R`.

```
inst/shiny/
  global.R              # library() calls, source() helpers, app constants
  ui.R                  # bslib page, single-screen layout
  server.R              # reactives, validation, rendering
  R/
    helpers.R           # pure functions: format_bf(), bf_label(), input checks
    plots.R             # omega-sensitivity curve, BF axis-of-evidence strip
  www/
    custom.css          # 20-40 lines of tweaks for the Jeffreys-scale strip
    NOTES.md            # one-paragraph "what this app shows" for shinyapps.io landing
  rsconnect/            # generated by rsconnect on first deploy; .gitignored
```
(`deploy.R` is NOT shipped in `inst/`; lives at repo root.)

Concrete contents:

**`inst/shiny/global.R`** (~20 lines)
- `library(shiny)`, `library(bslib)`, `library(DrWrinch)`, plot lib
  (see Decision A).
- `source("R/helpers.R", local = TRUE)`; `source("R/plots.R", local =
  TRUE)`. (Shiny auto-sources files in an `R/` subdir under the app
  dir as of Shiny 1.5; sourcing explicitly is belt-and-braces and
  clearer.)
- App-level constants: `JEFFREYS_BREAKS <- c(1, 3, 10, 30, 100)`,
  `JEFFREYS_LABELS <- c("anecdotal", "moderate", "strong", "very
  strong", "decisive")`, `THRESHOLD_DEFAULT <- 20`.

**`inst/shiny/ui.R`** (~100 lines)
- `bslib::page_sidebar()` (or `page_fillable` + `layout_sidebar`);
  `theme = bslib::bs_theme(bootstrap_version = 5, preset =
  "bootstrap")` (match `_pkgdown.yml`'s Bootstrap 5).
- Sidebar: input controls (see section 4).
- Main: a `bslib::navset_card_tab()` with three tabs --- "Result",
  "Sensitivity", "About". The "About" tab embeds a short paragraph
  plus a `bslib::card_body()` with rendered HTML mirroring the
  vignette's "when does each model apply?" table.

**`inst/shiny/server.R`** (~120 lines, hard cap before splitting into
modules)
- Standard `function(input, output, session)` signature.
- Reactives in order: validated inputs -> bf results -> sensitivity
  results -> plot data. See section 5.

**`inst/shiny/R/helpers.R`** (~80 lines)
- `validate_counts(y_W, y_R)`: returns a `shiny::validate(need(...))`
  chain. Why a separate function: same checks needed by both result
  and sensitivity render paths.
- `format_bf(bf)`: takes the numeric BF, returns a list of `value`
  (formatted string, e.g. "39.0" or ">10,000" or "undefined (RTF urn
  too small)"), `verdict` (Jeffreys label), `direction` ("favors
  working theory" / "favors rival" / "no evidence either way").
  Handles `NA_real_` and `Inf` explicitly. **Why** a single formatter:
  both models route their numerical outputs through the same UI prose,
  so non-R users see consistent language.
- `bf_label(bf)`: maps numeric BF to one of `JEFFREYS_LABELS` based on
  `cut()` against `JEFFREYS_BREAKS` (with the symmetric treatment of
  `1/bf` for BFs < 1).
- `interpret_omega_star(om)`: e.g., returns "Pro-H1 items would have
  to be roughly 30% more likely to be observed than pro-rival items
  for the conclusion to fail at threshold 20." Handles `0`, `NA`, and
  finite cases.

**`inst/shiny/R/plots.R`** (~80 lines)
- `plot_bf_vs_omega(y_W, y_R, model = c("binomial", "urn"), threshold)`:
  computes BF over `omegas <- exp(seq(log(0.25), log(8), length.out =
  80))` (log-spaced because BF is decreasing and the action is near
  1), draws horizontal line at `threshold`, vertical line at
  `omega_star` if defined. **Why log-spaced**: matches the
  monotone-decreasing structure of BF in omega and gives equal visual
  weight to omega < 1 (bias against H1) and omega > 1 (bias for H1).
- `plot_jeffreys_strip(bf)`: a simple discrete-color bar with markers
  --- useful because the target audience is humanists, not
  statisticians. Optional for MVP.
- `plot_bf_vs_M(y_W, y_R, threshold, M_max = 50)` for the binomial
  tab only: bar chart of BF at each rival-favoring pseudo-observation
  count.

## 2. Design decisions you should make explicitly

These are real choices. Each has a recommendation and a trade-off.

**Decision A --- Plot library: ggplot2 vs. plotly.**
- **Recommendation: ggplot2.** It's already in `Suggests`. The plots
  are small, static, and need to look right in a screenshot; plotly's
  interactivity (hover, zoom) is a nice-to-have here, not a need-to-
  have. Adding plotly means another heavy dependency that bloats
  shinyapps.io image size and slows cold-start.
- Trade-off: with ggplot2 you give up hover-tooltips on the omega
  curve. Mitigation: print the numeric `omega_star` with a clear
  annotation on the plot. If you later want interactivity, swap to
  plotly with one helper change.

**Decision B --- Tab vs. accordion vs. side-by-side for the two models.**
- **Recommendation: side-by-side cards on a single screen, sharing one
  set of inputs.** The whole point of the vignette is that you
  usually want both BFs reported together ("when in doubt, compute
  both"). Forcing the user to flip a tab to compare binomial-vs-urn
  defeats this.
- Trade-off: on narrow screens this stacks; that is fine on
  `bslib::layout_columns(col_widths = c(6,6))` which auto-collapses.
- Alternative if you prefer: a `radioButtons("model", ...)` with one
  card. Do not do this --- it hides the comparison.

**Decision C --- Should `theta_cut` and `prior_a`, `prior_b` be exposed?**
- **Recommendation: hide `theta_cut`, `prior_a`, `prior_b` behind a
  collapsible "Advanced" `bslib::accordion_panel`.** The target
  audience will not know what these are. Default to `theta_cut =
  0.5`, `prior_a = prior_b = 1`. Power users open the accordion.
- Trade-off: discoverability of the prior-sweep sensitivity feature.
  Mitigation: the "Sensitivity" tab text describes `M_star` ("M extra
  pseudo-observations favoring the rival") in plain prose regardless
  of whether the prior accordion is open.

**Decision D --- Should the app support the urn model's domain restriction gracefully?**
- **Yes, mandatory.** `bf_urn(2, 10)` returns `NA_real_`. The server
  must detect this and render a clear "the urn model is undefined
  here because the rival-favorable urn cannot supply a sample of size
  n = y_W + y_R when y_R > y_W + 1" message in the urn card, **while
  still showing the binomial result.** This is exactly the kind of
  friction that drives non-R users away if not handled.

**Decision E --- Single shinyapps.io account vs. team.**
- The plan author cannot decide this. If `rsconnect::accounts()`
  returns one for `jwbowers` already, deploy under that. Otherwise the
  user needs to register at https://shinyapps.io and run
  `rsconnect::setAccountInfo()`. Flag this at the deploy step.

**Decision F --- CRAN submission timing.**
- The plan author recommends submitting the current `0.0.0.9002` (four
  core functions, clean check) **first**, then adding `run_app()` in
  `0.0.1` afterward. Cleaner first submission; deploy script depends
  on the CRAN binary existing.

`shinytest2` and `rsconnect` should be conditionally loaded in tests
(`testthat::skip_if_not_installed`) and in `deploy.R`
(`requireNamespace` guard).

**Why not Imports for any of these:** the only entry point from the
rest of the package into the app is `run_app()`, which
`requireNamespace`-guards every Shiny call. A user who installs
DrWrinch just to compute Bayes factors should never need Shiny.

**Why a version floor on `shiny` and `bslib`:** `bslib::page_sidebar()`
and `bslib::navset_card_tab()` need bslib >= 0.6.
`shiny::bindEvent()`-style reactivity needs shiny >= 1.6. The floors
are conservative.

## 5. Server logic

Reactive graph (read top-down, dependencies flow downward):

```
inputs$y_W, inputs$y_R, inputs$threshold, ...
    |
    v
counts_ok  <- reactive({ validate(...); list(y_W = ..., y_R = ...) })
    |
    +---> bf_binom <- reactive({ bf_binomial(c$y_W, c$y_R, ...) })
    +---> bf_urn_v <- reactive({ bf_urn(c$y_W, c$y_R) })
    +---> sens_b   <- reactive({ sens_binomial(c$y_W, c$y_R, threshold) })
    +---> sens_u   <- reactive({ sens_urn(c$y_W, c$y_R, threshold) })
            |
            +---> output$result_binom (renderUI: card with formatted BF)
            +---> output$result_urn   (renderUI: card with formatted BF; NA-aware)
            +---> output$plot_omega   (renderPlot)
            +---> output$plot_M       (renderPlot)
            +---> output$tipping_text (renderUI: prose summary)
```

Key implementation choices:

1. **Wrap each model call in `tryCatch`** --- `bf_binomial()` uses
   `stats::integrate()` which can fail at pathological omega. Catch
   and render a friendly "computation failed at omega = X; try a
   narrower range" message rather than letting Shiny show a red
   error.
2. **Treat `NA_real_` (urn undefined) and `Inf` (rival probability
   zero) as expected branches**, not errors. The card renders prose
   explaining each.
3. **Debounce the omega-plot computation** with
   `shiny::debounce(200)` --- typing `y_W = 1, 17, 170` should not
   recompute the 80-point omega sweep three times. The numeric BF
   outputs do not need debouncing (microseconds).
4. **No global state, no `<<-`, no `reactiveValues` unless required.**
   Reactives + `eventReactive` if you add the `Recompute` button.
5. **Use `req()` early** to short-circuit when inputs are NULL during
   initial render (Shiny renders before user input).

## 6. Testing strategy

Three layers, prioritized:

**Layer 1 --- Pure helpers (testthat, runs in CI, fast).**
File: `tests/testthat/test-app_helpers.R`.
- `format_bf(39)` returns `verdict = "strong"`, `direction = "favors
  working theory"`.
- `format_bf(1)` returns `verdict = "no evidence"`, neutral direction.
- `format_bf(NA_real_)` returns `verdict = "undefined"` with
  explanatory text.
- `format_bf(Inf)` returns a high-evidence verdict, not a crash.
- `interpret_omega_star(0)` returns the "fails at baseline" prose.
- `interpret_omega_star(NA_real_)` returns the "robust to any bias"
  prose.
- `interpret_omega_star(1.304)` returns a numeric percentage
  interpretation.
- `bf_label()` maps boundaries (1, 3, 10, 30, 100) into the correct
  Jeffreys bin.

These tests **must** be written before the helpers are implemented
(per coding standards).

How they access the helper code: at the top, `source(system.file(
"shiny/R/helpers.R", package = "DrWrinch"))` after
`devtools::load_all()`. **Why** --- keeping helpers under
`inst/shiny/R/` and not under the package's own `R/` means they're not
part of the namespace; tests have to source them explicitly. The
alternative is to move helpers into `R/app_helpers.R` and export them
as `@keywords internal`, which is recommended only if a third test
layer ends up needing them.

**Layer 2 --- Server logic (testthat + `shiny::testServer`).**
File: `tests/testthat/test-app_server.R`.
`skip_if_not_installed("shiny")`.
- Construct a `testServer(app = "inst/shiny", expr = { ... })` block.
- Set `session$setInputs(y_W = 7, y_R = 3, threshold = 20)` and assert
  `bf_binom() ~= 7.83`, `bf_urn_v() == 39`, `sens_u()$omega_star ~=
  1.304`.
- Set `y_W = 2, y_R = 10` and assert `bf_urn_v()` is `NA` and the urn
  card output contains "undefined".
- Set `y_W = 5, y_R = 5` and assert both BFs are 1.

These are substantive in the sense the coding standards require: they
test the principle that the app **correctly translates the paper's
claims** into UI state, not just that it does not crash.

**Layer 3 --- Snapshot/visual (`shinytest2`, runs locally only).**
File: `tests/testthat/test-app_snapshot.R`. Top: `skip_on_cran()`,
`skip_on_ci()` (or skip on CI unless you wire up a headless Chrome
action), `skip_if_not_installed("shinytest2")`.
- One snapshot of initial render at `y_W = 7, y_R = 3`.
- One snapshot of the urn-undefined branch.
- One snapshot of the sensitivity tab.

`shinytest2` snapshots are large and fragile across OSes; keep these
to a handful and skip on CRAN.

Update `tests/testthat.R`: no change needed, `test_check("DrWrinch")`
already picks up new files.

## 7. Deployment to shinyapps.io

The constraint is one source of truth: the same `inst/shiny/` dir
runs locally via `run_app()` and gets deployed to shinyapps.io.
That's straightforward because `rsconnect::deployApp(appDir =
"inst/shiny")` packages exactly that directory.

**File: `deploy.R` at repo root** (not under `inst/`, not shipped):
- Top: `if (!requireNamespace("rsconnect", quietly = TRUE))
  install.packages("rsconnect")`.
- Then: short comment about needing `rsconnect::setAccountInfo(...)`
  first time.
- Body:
  ```r
  rsconnect::deployApp(
    appDir   = "inst/shiny",
    appName  = "drwrinch",
    appTitle = "DrWrinch: Bayes factors for process tracing",
    appFiles = c("global.R", "ui.R", "server.R", "R/helpers.R",
                 "R/plots.R", "www/custom.css"),
    forceUpdate = TRUE
  )
  ```
- The explicit `appFiles` allowlist prevents accidental deployment of
  `rsconnect/`, `NOTES.md`, or any local `.RData`.

**Critical**: shinyapps.io does not have DrWrinch installed. The app
must depend on the package as published. Two options:

**Option 1 (recommended for the medium term): publish DrWrinch to CRAN
first, then deploy.** The `library(DrWrinch)` in `global.R` resolves
cleanly against the CRAN binary. This is the cleanest path and aligns
with the existing `cran-comments.md`.

**Option 2 (for the demo before CRAN): use `remotes::install_github()`
in a setup step.** rsconnect does not run arbitrary setup, but it
does honor the package manifest written by
`rsconnect::writeManifest()`. The hack: add `if
(!requireNamespace("DrWrinch")) remotes::install_github("bowers-
illinois-edu/DrWrinch")` at the top of `global.R`. This works but
slows cold-start by ~30s and is fragile to GitHub rate limits. Use
only as a stopgap.

**Recommendation: go with Option 1.** It also gives you the CRAN
release as a natural milestone.

**`.Rbuildignore` additions** (re-stating from 1c, with reasons):
- `^deploy\.R$` --- repo helper, not part of the package.
- `^inst/shiny/rsconnect$` --- generated per-deploy state.
- `^inst/shiny/www/NOTES\.md$` --- landing-page notes for
  shinyapps.io, not for the R package tarball.

## 8. CRAN-readiness

Specific things `R CMD check` is going to complain about if we are not
careful:

1. **`run_app()` examples block.** Wrap in `\dontrun{}` (not
   `\donttest{}` --- even `--run-donttest` will time out). The
   roxygen example block is already drafted this way in section 1.
2. **`inst/shiny/` size.** Keep `www/` to essentials: 1 small CSS
   file (~2KB). No fonts, no images, no bundled JS libraries.
   shinyapps.io will load Bootstrap from CDN via bslib.
3. **`Suggests` not actually optional?** CRAN flags `Suggests`-listed
   packages that the package uses unconditionally. Verify: every
   `library()` in `global.R` and `source()` in `helpers.R/plots.R` is
   inside `inst/`, so `R CMD check`'s static analysis will not see
   them. The only package-side reference is `requireNamespace()` calls
   in `R/run_app.R`, which is correct.
4. **`No visible binding for global variable`** notes from `R CMD
   check` on ggplot's aesthetics. Mitigation: in `plots.R`, declare
   with `utils::globalVariables(c("omega", "bf"))` at the top of the
   file, or use `aes(x = .data$omega, ...)` with `@importFrom rlang
   .data`. Since helpers live under `inst/`, `R CMD check` will not
   actually scan them --- but if you later move helpers into `R/`,
   this becomes load-bearing.
5. **Spell-check.** Add "shinyapps", "Jeffreys", "bslib" to
   `inst/WORDLIST` if you run `devtools::spell_check()`.

The package is at `0.0.0.9002` with `cran-comments.md` ready.
**Decision F: do you want to land the Shiny app *before* the first
CRAN submission, or push CRAN out for it?** Recommendation: submit
to CRAN first at the current state (it's clean, the four core
functions are the contribution), then add `run_app()` in `0.0.1` as a
follow-up release. This keeps the first CRAN submission simple and

## 10. Risks and things to flag now

1. **shinyapps.io free tier limits.** 5 active hours/month and
   concurrency caps. For a paper-demo audience this is usually fine
   but is worth noting if the paper goes viral. The deploy script
   can be re-pointed to Posit Connect Cloud or RStudio Connect later
   with one URL change.
2. **`BiasedUrn::dFNCHypergeo` on shinyapps.io.** This is on CRAN, so
   it will install cleanly. No risk.
3. **Cold start time.** shinyapps.io spins down idle apps after ~5
   min. First hit after sleep takes 10--20s. Mitigation: a small
   "scheduled keep-warm" GitHub Action that curls the URL every 4
   minutes during business hours. Out of scope for MVP.
4. **Mobile usability.** Process-tracing scholars at conferences may
   pull this up on phones. `bslib::page_sidebar()` collapses the
   sidebar to a drawer on small screens by default; verify on a
   phone before finalizing.
5. **Reproducibility of `omega_star`.** The vignette claims `~= 1.3`
   for `(7, 3)`. The Shiny app must show numbers that exactly match
   the package, since the vignette and the app share a citation. The
   server should call `sens_urn()` directly rather than recomputing
   the search itself.
